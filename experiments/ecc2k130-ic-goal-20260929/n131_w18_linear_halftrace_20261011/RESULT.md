# Linear halftrace preserves the exact W18 seed join and removes repeated squaring

The W18 selected-seed join uses the linearity of halftrace over `GF(2)` to compute a 131-image basis table once per charged query. For each later field element it XORs the images of its set polynomial-basis bits. The three frozen queries produced byte-identical pair tables and identical untimed solver outputs to the independently checked-Sage archived implementation. The charged basis setup replaces **12,844,390–12,874,810** repeated halftrace squarings per query with **17,030** basis-image squarings and XOR evaluation. This is a point-decomposition kernel improvement inside the existing exact four-atom join.

For odd extension degree 131, `H(x) = sum_{j=0}^{65} x^(2^(2j))` is `GF(2)`-linear. With `e_i=t^i`, `H(x)=XOR_{i:bit_i(x)=1} H(e_i)`. The native implementation builds all 131 images after the query clock starts, then applies this identity for each source-pair quadratic, each left pair output, and the supplied query output. It retains the original pair-equation check, trace check, S3 check, column check, and table serialization. The executable and all inherited sources are hash-bound in the [frozen protocol](protocol.json).

The curve is `EC1N131Ckb1heb5f1998f20b` over `GF(2)[t]/(t^131+t^13+t²+t+1)`. The W18 support contains **1,575,684** distinct usable factor-base points before signed-Frobenius folding and **131,068** effective columns. Each query used one worker, a 120-second native cap, a 130-second parent cap, and a 4-GiB process RSS cap. The charged interval begins after loading reusable rational-mask support and includes basis initialization, selected-seed pair construction, table serialization, left-output preparation, S3 candidate generation, lookup, and column checks. The seed and output `z` are supplied test inputs; the result is a component measurement with `candidate_id: null`.

The executable was built on arm64 macOS with Apple clang 17.0.0 using `clang++ -std=c++17 -O3 -Wall -Wextra native.cpp -o native`. The frozen protocol records the resulting executable SHA-256 and every inherited source and input SHA-256.

These are exploratory paired CPU times from an unisolated host. The corresponding archived run took 3.611–5.156 seconds with the same baseline executable, showing substantial host variation. The deterministic squaring count and exact-output equivalence establish the kernel change; a controlled wall-time ratio requires the repository's host-isolation receipt. The query phase remained roughly 2 seconds in this local run, so later optimization should focus on exact S3 candidate generation and lookup as well as seed selection.

The first four case runs completed before an `ENOSPC` interruption while writing the receipt. The [resume source](resume.py) completed the third case after the duplicate tables were verified against the archived table hashes and removed to free space. The [run receipt](run_receipt.json) records all six executions, raw outputs, exact table hashes, parent intervals, child RSS, and the resume source hash. The [audit](audit.json) checks every case against the archived raw result and exact table digest, verifies the source/input chain and caps, and checks the exclusive build plus lookup phase sum. The archived [Sage validation](../n131_w18_ondemand_seedjoin_20261011/validation.json) independently replayed the exact tables and S3 roots; the byte matches transfer that validation to these runs.

The next algorithm step is a target-conditioned proposal rule for the seed and both block outputs. A useful rule must preserve every genuine witness while rejecting enough prefixes before these charged seed joins. The single-target online and rho comparison can follow once such a rule yields ordinary relations under the frozen N131 resource cap.
