# Paired isolated scalar multiplication panel

The sparse 13-row tau-six comb and the 10-row GLV comb now have a frozen,
point-verified comparison on the same 129 public scalars. The panel contains
128 previously frozen `holdout_random` scalars in source order and one scalar
whose top-row orbit is omitted from the sparse table. The reference is
`--benchmark-scalar-glv-comb10-fixed-case`; the candidate is
`--benchmark-scalar-w6-comb13-sparse-fixed-case`. Both use the standard
secp256k1 generator and the same native executable.

## Frozen input and timing boundary

`tau6-comb13-bench-fixture.json` is generated by
`make_tau6_comb13_bench_fixture.py` from the frozen
`tau6-comb13-sparse-result.json` panel. Expected points are independently
computed by `lazy_tau_screen.point_multiply` and checked by each native case.
The fixture SHA-256 is
`2895d9c40912b090f0e6ce85ef8bb4d92822a83a5626fb376fcb552a556981fb`.
The source result SHA-256 is
`89c330fd5c8f9a9ac0a1e9d884b03a5d09fb7e749e6948af597c263472f2a8a2`.

The native `online_ms` starts after fixture loading, scalar decoding,
constant initialization, and the relevant fixed-generator table construction.
It includes scalar reduction and recoding, point evaluation, affine
conversion, and the expected-point assertion. The timed result is one scalar
multiplication on one public point. Table construction is reusable setup and
must be reported separately if setup-inclusive cost is studied. Both methods
are variable-time and intended for public-scalar research workloads.

The runner alternates reference/candidate order by case and repetition. The
default seven repetitions yield 903 verified pairs when every run passes.
The runner records raw runs and returns an aggregate speedup only if all pairs
and the host isolation and noise gates pass. Preserve rejected manifests and
preflight receipts with the result; a rejection has unknown speedup.

## Reproduce on a qualifying Linux host

Use the exact repository snapshot containing this protocol. Build the native
binary on that host. The following paths and CPU IDs are examples; replace
them with the verified host topology and isolated cgroup before dispatch.
The persistent queue and service are described in
[`docs/ISOLATED_BENCHMARKS.md`](../../docs/ISOLATED_BENCHMARKS.md).

```sh
cd /workspace/cryptanalysis
export CARGO_TARGET_DIR=/workspace/build/prime-j0-native
cargo build --manifest-path experiments/prime-j0-secp256k1-native/Cargo.toml \
  --offline --locked --release --bin eisenstein_fixed

python3 experiments/prime-j0-secp256k1-native/make_tau6_comb13_isolated_manifest.py \
  --repo-root /workspace/cryptanalysis \
  --binary /workspace/build/prime-j0-native/release/eisenstein_fixed \
  --cgroup /sys/fs/cgroup/benchmark-isolated \
  --cpus 4-5 --execution-cpu 4 --mem-node 0 \
  --output /workspace/isolated-bench/tau6-comb13-paired.json

python3 scripts/isolated_bench.py probe \
  /workspace/isolated-bench/tau6-comb13-paired.json
python3 scripts/isolated_bench.py --queue-root /workspace/isolated-bench submit \
  /workspace/isolated-bench/tau6-comb13-paired.json
```

The host administrator must reserve the full SMT sibling group, move IRQs and
housekeeping work away, set fixed frequency and NUMA policy, and keep the
service outside the isolated cgroup. The submitted manifest records the
binary, source, runner, fixture, panel, and protocol hashes. Inspect
`preflight.json`, `runs.jsonl`, `pairs.jsonl`, and `summary.json` in the job
receipt before citing any timing ratio.
