# ECC2K-130 source-correlated GPU profile, 2026-10-14

## Frozen diagnostic before execution

The previous isolated profile and four paired screens leave the Frobenius walk's
source-level stall sequence unidentified. This run uses the same pinned public
CUDA source commit `1f8e6847de9e207880bd3be63835c3f56eb182d5`, production
v3 settings, one RTX PRO 6000, 120,320 workers, 64 steps, run ID 11000 and
DP32. The driver passes `-lineinfo` explicitly so Nsight Compute can
correlate CUDA lines with SASS; the Makefile already supplies that flag, so
this duplicate flag is not a newly introduced build mode. Source import and
the source-page export are the new profiler steps. The profile is diagnostic,
not the ordinary timing baseline.

The driver [profile_source_correlated.py](../kernelagent-20261013/profile_source_correlated.py)
loads every runner source file from that commit, records their hashes, builds
`sm_120`, runs one ordinary launch, then profiles one kernel launch with
`SourceCounters` and the prior aggregate sections. Application replay creates a
fresh DP file for every pass. The run records the exact profiler command,
compiler and driver versions, binary hash, replay output, replay pass IDs,
unique DP paths, imported raw/details and CUDA/SASS source tables, and the
native `.ncu-rep` with a verified transfer hash. A run lacking any of these is
preserved as a diagnostic failure, not promoted to bottleneck evidence.

```sh
python3 -m py_compile ecc2k130/runner/research/kernelagent-20261013/profile_source_correlated.py
modal run ecc2k130/runner/research/kernelagent-20261013/profile_source_correlated.py \
  --output ecc2k130/runner/research/kernelagent-20261014/source-correlated-profile.json \
  > ecc2k130/runner/research/kernelagent-20261014/source-correlated-profile.log 2>&1
```

The code and this protocol are committed before that command. A source/SASS
table with a concentrated, interpretable PC stall sequence permits one
default-off candidate aimed at that sequence. Stall samples attach to the
waiting instruction, so a proposed change must inspect its producing
instructions too. An empty or ambiguous table leads to a bounded compiled
sequence probe and no production speed claim.

Any candidate first owes independent host arithmetic, the frozen 355-record
sorted DP32 corpus with zero drops, and fresh/checkpoint/resume compatibility.
Then it owes two alternating 64-launch paired screens with an A/A control; both
candidate ratios must exceed the A/A range before five warmed 128-launch
confirmation pairs. End-to-end cloud cost and target recovery remain separate
measurements.

2,000–2,761 short-scoreboard samples each. Samples attach to waiting
instructions, and line mapping around inlined arithmetic is approximate;
these observations do not assign wall time to one source statement.

The prior static-barrier and root-barrier screens were flat or slower, so the
next bounded candidate targets the carryless product dependency. The
default-off `ECC_PACKED_CLMAD_HI_FIRST=1` path in `packed131.h` issues the
high half before the low half in `clmul64`, leaving the polynomial product
and reduction unchanged. The hypothesis is that an earlier high-half result
reduces waiting on its Karatsuba XOR consumers. The compiler may choose the
same SASS schedule, or the change may increase register pressure; either is
possible. This candidate is selected from the source profile, not from a
timing result.

### Same-group 256-thread geometry (frozen before execution)

The source profile also recorded 79,014 not-issued `stall_wait` samples and
about 41% achieved occupancy for one 640-thread block per SM. The next
candidate changes only `THREADS=256`, keeping 120,320 workers, four-warp
inverse groups, batch 16, and all arithmetic settings fixed. This makes 470
blocks with two inverse groups each, versus 188 blocks with five groups each;
both layouts have 940 inverse groups and the same number of field inversions
and group barriers. More blocks may give the scheduler more runnable warps,
but the extra block overhead may outweigh that. Source samples alone do not
predict the outcome. Earlier 128-thread static-barrier and 320-thread
two-warp screens changed other conditions and do not answer this comparison.

Use the same pinned production source, A/A arm, two alternating 64-launch
pairs, run ID 11000, DP32, and the same 355-record sorted hash. Require zero
drops and matching corpora for every arm. Only both candidate ratios above
the A/A interval advance to five warmed 128-launch pairs and full
fresh/checkpoint/resume checks. A compile, launch or corpus failure is
preserved as a separate outcome. This is a launch-geometry hypothesis; it
does not alter production defaults.


### Three-product high-half batch (frozen before execution)

The smaller high-half-first change had a sub-percent apparent gain within A/A
noise. To target more of the repeated high-half consumer stalls, the next
default-off `ECC_PACKED_CLMUL_HI_BATCH=1` path in `packed131.h` issues the
three independent `clmad.hi.u64` operations of a 128-bit Karatsuba product
before its three `clmad.lo.u64` operations. It uses the same six carryless
operations, fold, top correction, and reduction as the baseline. The existing
`PACKED_CLMUL_FLAT` path did the reverse order under an earlier profile; this
is a different instruction schedule. The hypothesis is a longer producer to
consumer interval for the high-half XOR fold, with possible costs from longer
register lifetimes or ptxas reordering. The candidate flag is off by default
and is independent of the first high-half-first flag.

Run the host field and walk gate, then two alternating 64-launch GPU pairs
against the same pinned baseline with a production A/A arm. The screen
requires the same 355-record DP32 sorted hash and zero drops in every arm.
Only if both candidate ratios exceed the A/A interval will it advance to
five warmed 128-launch pairs and fresh/checkpoint/resume checks. Preserve
build failures, different DP corpora, and regressions as separate outcomes.
No instruction-sample ratio is a useful-update speed measurement.
