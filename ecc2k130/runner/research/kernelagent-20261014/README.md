# ECC2K-130 source-correlated GPU profile, 2026-10-14

## Frozen diagnostic before execution

The previous isolated profile and four paired screens leave the Frobenius walk's
source-level stall sequence unidentified. This run uses the same pinned public
CUDA source commit `1f8e6847de9e207880bd3be63835c3f56eb182d5`, production
v3 settings, one RTX PRO 6000, 120,320 workers, 64 steps, run ID 11000 and
DP32. The driver passes `-lineinfo` explicitly so Nsight Compute can
correlate CUDA lines with SASS; the Makefile already supplies that flag, so
this duplicate flag is not a newly introduced build mode. Source import and
the source-page export are the new profiler steps. The profile is diagnostic,
not the ordinary timing baseline.

The driver [profile_source_correlated.py](../kernelagent-20261013/profile_source_correlated.py)
loads every runner source file from that commit, records their hashes, builds
`sm_120`, runs one ordinary launch, then profiles one kernel launch with
`SourceCounters` and the prior aggregate sections. Application replay creates a
fresh DP file for every pass. The run records the exact profiler command,
compiler and driver versions, binary hash, replay output, replay pass IDs,
unique DP paths, imported raw/details and CUDA/SASS source tables, and the
native `.ncu-rep` with a verified transfer hash. A run lacking any of these is
preserved as a diagnostic failure, not promoted to bottleneck evidence.

```sh
python3 -m py_compile ecc2k130/runner/research/kernelagent-20261013/profile_source_correlated.py
modal run ecc2k130/runner/research/kernelagent-20261013/profile_source_correlated.py \
  --output ecc2k130/runner/research/kernelagent-20261014/source-correlated-profile.json \
  > ecc2k130/runner/research/kernelagent-20261014/source-correlated-profile.log 2>&1
```

The code and this protocol are committed before that command. A source/SASS
table with a concentrated, interpretable PC stall sequence permits one
default-off candidate aimed at that sequence. Stall samples attach to the
waiting instruction, so a proposed change must inspect its producing
instructions too. An empty or ambiguous table leads to a bounded compiled
sequence probe and no production speed claim.

Any candidate first owes independent host arithmetic, the frozen 355-record
sorted DP32 corpus with zero drops, and fresh/checkpoint/resume compatibility.
Then it owes two alternating 64-launch paired screens with an A/A control; both
candidate ratios must exceed the A/A range before five warmed 128-launch
confirmation pairs. End-to-end cloud cost and target recovery remain separate
measurements.

### Three-product high-half batch (frozen before execution)

noise. To target more of the repeated high-half consumer stalls, the next
default-off `ECC_PACKED_CLMUL_HI_BATCH=1` path in `packed131.h` issues the

## Current limit and next experiment

The source profile localizes much of the sampled barrier activity to the

frozen production workload beyond its same-allocation A/A spread. Three new

## Double-buffered grouped inverse: frozen protocol before execution

The default-off `ECC_INVERSE_DOUBLE_BUFFER=1` candidate gives consecutive
grouped inverse calls separate shared-memory banks, selected by the walk
step's parity, and omits the final group barrier. It changes no field
arithmetic or walk inputs. The predicted benefit is one fewer group barrier
per inverse. Its cost is another `5 * ECC_THREADS * sizeof(uint32_t)` bytes
of shared memory and a bank-address calculation; resource or scheduling costs
may exceed the saved synchronization.

The synchronization argument applies to a full grouped block with the same
step loop for every warp. Each call's last downward-level barrier precedes
every lane's final read. A warp may begin the next call before another warp
finishes that read, but the next call writes the other bank. Before any warp
can enter the call two steps later and reuse the old bank, it must pass the
next call's first group barrier, which waits for every warp in the group to
enter that call. Each warp must have finished its prior read before entering.
The first call writes its chosen bank before its first barrier; the last call
does not need a later reuse. Zero inputs follow the same barriers after the
existing replacement by one. The fallback tail is selected for an entire
block and does not touch group scratch. This argument assumes CUDA's group
barrier provides the required shared-memory ordering; a device race check is
an independent gate, not a substitute for the argument.

The [gate driver](double_buffer_gate.py) first builds the production binary
with CUDA `sm_120`, records ptxas resources and exact hashes, then tests the
inverse against the independent device reference at 512 threads for all
supported group widths and at the production 640 threads for four-warp
groups. It runs `compute-sanitizer --tool racecheck` at 640 threads with
different group loop counts and repeated bank reuse. A missing race checker,
build failure, reference mismatch, race report, or ambiguous checker output
stops before timing and remains a distinct receipt. Run the existing host
field/walk gate as an additional check; it does not exercise the new shared
scratch. Preserve each raw log and machine-readable result.

If those gates pass, run the same pinned production baseline, A/A arm, two
alternating 64-launch pairs, 120,320 workers, batch 16, four-warp groups,
run ID 11000 and DP32. Every timing arm must reproduce the frozen 355-record
sorted corpus SHA-256
`c80bb8db34e419d53bc946a5fef01c99fd60214a16f9b42ff87b5d52f3668a90`
with zero drops. Only two candidate ratios above the A/A interval advance
to five warmed 128-launch pairs and fresh/checkpoint/resume checks. Keep the
switch off by default unless all compatibility and performance gates pass.
The screen measures useful update throughput for this one GPU and workload;
it does not measure full cloud or ECDLP cost.

Compute Sanitizer on the RTX PRO 6000. It compiles two 64-thread kernels:
one writes a shared word in one lane and synchronizes before all lanes read;
the other has two lanes write that word without ordering. A usable checker
must report zero hazards for the first and a planted write-after-write hazard
for the second. Capture the GPU, driver, compiler, checker version, reported
confidential-compute mode, exact commands, source/binary hashes, raw output,
and exit status. If the first control says `Device not supported`, preserve
that result without treating the candidate as checked.
